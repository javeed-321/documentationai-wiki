## Trigger

Use this runbook when Notion users report that Enterprise Search returns incomplete results, an agent stops completing routine work, Meeting Notes stop appearing, or a workspace sync looks stale. Treat any change in permissions, connector health, or indexing latency as a trigger to inspect the workspace before users escalate further.

Common signals include delayed updates in docs, missing pages in search results, agent tasks that fail repeatedly, or integrations that stop passing content into the workspace. If the issue affects multiple teams or blocks time-sensitive work, move immediately to the step sequence below.

## Steps

<Steps>
  <Step title="Confirm the symptom" icon="check-circle">

    Identify the scope before you change anything.

    Run a quick check in the workspace and capture the exact failure mode:

    ```bash
    curl -I https://www.notion.so/product/enterprise-search
    ```

    Verify whether the issue is:
    - search results missing recent content
    - an agent returning errors or stopping early
    - Meeting Notes not generating
    - a connector not refreshing data
    - permissioned content appearing incorrectly

  </Step>
  <Step title="Check workspace health" icon="shield">

    Review the workspace status, recent changes, and any permission updates. Confirm that the affected pages, databases, and teamspaces still have the intended access model.

    Use these checks:
    - confirm the workspace is reachable
    - confirm the relevant pages still exist
    - confirm recent permission changes are expected
    - confirm the affected users belong to the right groups

    If the issue is limited to a single teamspace, focus on that scope before expanding.

  </Step>
  <Step title="Validate Enterprise Search indexing" icon="search">

    Check whether search is lagging behind recent edits or missing a content source. Enterprise Search depends on current workspace content and healthy source connections.

    Compare a recent edit against search results:
    - create or locate a page that changed recently
    - search for a unique phrase from that page
    - confirm the page appears with current content

    If the page does not appear, inspect connector refresh timing and indexing delay. If several sources fail together, treat it as an integration issue rather than a single-page issue.

  </Step>
  <Step title="Recover a failed agent" icon="refresh-cw">

    If an agent is looping, timing out, or returning incomplete work, stop the failing run and restart from a clean prompt or task definition.

    Example operator check:

    ```bash
    notion-cli agents status --workspace "Operations"
    notion-cli agents restart --agent "workspace-triage"
    ```

    Then verify:
    - the agent has the correct permissions
    - the task instructions are still valid
    - the agent can read the source pages it needs
    - the output destination still exists

    If the agent depends on a broken connector, fix the connector first and rerun the job.

  </Step>
  <Step title="Inspect sync and integration health" icon="database">

    Check the data path from external systems into Notion. A stale sync usually means the connector stopped refreshing, permissions changed, or the source system returned an error.

    Example checks:

    ```bash
    notion-cli integrations list --workspace "Operations"
    notion-cli integrations logs --last 50
    ```

    Confirm:
    - the integration is still connected
    - refresh jobs are completing
    - the source account still has access
    - mapped databases still match the source schema

    If a schema change landed upstream, update the mapped fields and rerun the sync.

  </Step>
  <Step title="Verify security and permissions" icon="lock">

    Make sure the workspace is not exposing restricted content or hiding content from approved readers.

    Check:
    - page-level access
    - teamspace membership
    - guest access
    - database sharing rules
    - connector permissions

    If the problem is permission-related, correct access first and retest Enterprise Search or the affected agent. Permission fixes often resolve both missing results and failed task execution.

  </Step>
</Steps>

### Quick checks

Use these literal checks during triage:

```bash
# Confirm search is responding
curl -s https://www.notion.so/product/ai | head -n 5

# Inspect recent integration activity
notion-cli integrations logs --workspace "Operations" --last 20

# Re-run a failed agent task
notion-cli agents run --agent "workspace-triage" --task "rebuild report"
```

If you need a manual sanity check, open the affected workspace pages and confirm the expected content is visible, searchable, and editable by the right users.

## Escalation Path

<Callout kind="alert">

Escalate immediately if the issue affects multiple teamspaces, if search returns incorrect permissioned content, if a connector is repeatedly failing after a retry, or if an agent is acting on the wrong source data. Do not keep retrying a broken workflow without identifying the cause.

</Callout>

Escalate in this order:

1. Workspace owner or on-call operator
2. Notion admin for permissions or access changes
3. Integration owner for connector or sync issues
4. Security reviewer if restricted content is exposed or hidden incorrectly

Include these details in the escalation note:
- affected workspace or teamspace
- exact symptom
- time the issue started
- last successful sync or agent run
- recent permission or schema changes
- the commands you ran and their output

## Rollback

Roll back only the change that introduced the failure. Keep the rollback narrow so you do not hide a separate issue.

Use this sequence:

1. Restore the previous permission set if access changes caused the issue.
2. Revert the last connector mapping if a schema update broke sync.
3. Disable the failing agent if it is producing bad output or repeating failures.
4. Restore the prior page or database structure if a content change broke search expectations.
5. Rerun validation after each rollback step.

Example rollback commands:

```bash
notion-cli agents disable --agent "workspace-triage"
notion-cli integrations rollback --workspace "Operations" --source "crm-sync"
notion-cli permissions restore --workspace "Operations" --snapshot "before-change"
```

After rollback, confirm:
- Enterprise Search returns the expected page
- agents can read the correct sources
- sync jobs complete successfully
- permissions match the approved state

If rollback does not clear the issue, stop changing the workspace and escalate with the evidence you collected.
