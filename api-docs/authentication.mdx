## Overview

Stripe authenticates requests with API keys and webhook signatures. You use a secret key on the server, a publishable key in client-side code, and restricted keys when you want to limit access to a smaller set of permissions. For webhook delivery, you verify the signature in the `Stripe-Signature` header to confirm that Stripe sent the event.

Keep credentials separate by environment. Use test keys in development and live keys in production. Never expose a secret key in browser code, mobile code, or public repositories.

### Authentication model

| Credential | Use it for | Where it belongs |
| --- | --- | --- |
| Secret key | Server-side API requests | Secure backend only |
| Publishable key | Client-side initialization and tokenization flows | Browser or app client |
| Restricted key | Limited server-side access to specific resources | Secure backend only |
| Webhook signing secret | Verifying webhook payloads | Webhook handler only |

  <Tab title="Webhook signature" icon="check-circle">

Use the webhook signing secret to validate incoming webhook events. Verify the raw request body and the `Stripe-Signature` header before you trust the payload.

<ParamField header="Stripe-Signature" param-type="string" required="true">
  The signature header Stripe sends with each webhook request.
</ParamField>

<CodeGroup tabs="cURL,Node.js,Python">
  ````bash
curl https://api.example.com/webhook \
  -H "Stripe-Signature: t=12345,v1=abcdef123456"
  ````

  ````javascript
import crypto from "crypto";

function verifySignature(rawBody, signatureHeader, webhookSecret) {
  const expected = crypto
    .createHmac("sha256", webhookSecret)
    .update(rawBody, "utf8")
    .digest("hex");

  return expected === signatureHeader;
}
  ````

  ````python
import hmac
import hashlib

def verify_signature(raw_body, signature_header, webhook_secret):
    expected = hmac.new(
        webhook_secret.encode("utf-8"),
        raw_body.encode("utf-8"),
        hashlib.sha256,
    ).hexdigest()

    return hmac.compare_digest(expected, signature_header)
  ````

## Implementation details

Use server-side code to create and store privileged credentials, and use client-side code only for publishable operations. When you rotate a secret key, update every backend service that depends on it before you disable the old key.

<Steps>
  <Step title="Create the right key" icon="key">
    Decide whether you need a secret key, a restricted key, or a publishable key.

    - Secret keys are for server-side requests.
    - Restricted keys are for limited server-side access.
    - Publishable keys are for client-side flows.

  </Step>
  <Step title="Store the key securely" icon="lock">
    Place secret and restricted keys in environment variables or a secret manager.

    - Never commit credentials to source control.
    - Never send secret credentials to the browser.
    - Separate test and live credentials by environment.

  </Step>
  <Step title="Send authenticated requests" icon="send">
    Include the credential in the correct header or request body, depending on the operation.

    - Use `Authorization: Bearer ...` for secret and restricted keys.
    - Use the publishable key only where client-side code requires it.
    - Verify webhook signatures with the raw payload and header value.

  </Step>
  <Step title="Rotate and revoke" icon="refresh-cw">
    Rotate keys on a schedule and revoke keys you no longer need.

    - Replace keys in all deployed services.
    - Confirm webhook verification still passes after rotation.
    - Remove unused restricted permissions.

  </Step>
</Steps>

## Security tips

<Callout kind="alert">
  Treat secret keys and webhook signing secrets as sensitive credentials. Do not expose them in client code, logs, build output, or error messages. If you suspect a credential leak, revoke it immediately and rotate every dependent integration.
</Callout>

### Recommended practices

- Use separate test and live credentials.
- Scope restricted keys to the smallest necessary permission set.
- Verify webhook signatures on the raw request body.
- Store secrets in environment variables or a secret manager.
- Audit key usage regularly and revoke unused credentials.

### Common mistakes

- Using a secret key in browser code.
- Reusing one key across test and live environments.
- Trusting webhook payloads without signature verification.
- Giving a restricted key broader access than it needs.
- Hard-coding keys in source files or documentation examples.
