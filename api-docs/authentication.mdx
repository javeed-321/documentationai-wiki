## Overview

Use Vercel authentication to authorize API requests from scripts, services, and user-facing applications. The platform supports personal access tokens, OAuth apps, and team-based access controls so you can choose the right model for automation, delegated access, or organization-wide usage.

For most developer workflows, you send a bearer token in the `Authorization` header. For end-user integrations, you typically use OAuth and request only the scopes you need. For team-scoped automation, make sure the token or OAuth grant is tied to the correct team before you call an API endpoint.

## Authentication methods

Choose the method that matches how your integration runs and who owns the access.

<Tabs>
  <Tab title="Personal access tokens" icon="lock">
    Personal access tokens are best for private automation and server-to-server calls. You create the token in your Vercel account, then send it as a bearer token with each request.

    Use a personal access token when:

    - You own the automation and do not need end-user consent.
    - You run scheduled jobs, local scripts, or CI pipelines.
    - You need a simple header-based credential flow.

    A token usually inherits the permissions of the account or team that created it, so keep the scope as narrow as possible.
  </Tab>
  <Tab title="OAuth apps" icon="users">
    OAuth apps are best when you build an integration that acts on behalf of a user. The user grants access to specific resources during the authorization flow, and your app receives a token tied to that grant.

    Use OAuth when:

    - You need delegated access from a user.
    - You want users to connect their Vercel account without sharing a long-lived secret.
    - You need revocable access with explicit consent.

    Always request only the scopes your app needs, and verify the team or account context before you make changes.
  </Tab>
  <Tab title="Team access controls" icon="shield">
    Team-based access controls help you limit what an integration can do inside an organization. When a request targets team resources, confirm that the token or OAuth grant belongs to that team.

    Use team-based controls when:

    - You automate work across a specific team.
    - You need to separate production and staging access.
    - You want to reduce accidental cross-team changes.

    If your integration supports multiple teams, make the team identifier explicit in your configuration and validate it before each request.
  </Tab>
</Tabs>

## Personal access tokens

A personal access token is a long-lived secret that identifies an authorized user or team context. Send it in the `Authorization` header as a bearer token.

<ParamField header="Authorization" param-type="string" required="true">
  Bearer token used to authenticate the request.
</ParamField>

<ParamField header="x-vercel-team-id" param-type="string" required="false">
  Optional team identifier when the request must target a specific team context.
</ParamField>

Use this pattern for scripts and server-side jobs:

<CodeGroup tabs="cURL,JavaScript,Python">
  ```bash
  curl -X GET "https://api.example.com/v1/projects" \
    -H "Authorization: Bearer YOUR_PERSONAL_ACCESS_TOKEN"
  ```

  ```javascript
  const response = await fetch("https://api.example.com/v1/projects", {
    method: "GET",
    headers: {
      Authorization: "Bearer YOUR_PERSONAL_ACCESS_TOKEN",
    },
  });

  const data = await response.json();
  ```

  ```python
  import requests

  response = requests.get(
      "https://api.example.com/v1/projects",
      headers={
          "Authorization": "Bearer YOUR_PERSONAL_ACCESS_TOKEN",
      },
  )

  data = response.json()
  ```
</CodeGroup>

## OAuth apps

OAuth lets a user authorize your integration without exposing their password or sharing a static token. Your app redirects the user to Vercel for consent, receives an authorization code, and exchanges that code for an access token.

<Tabs>
  <Tab title="Authorization code" icon="arrow-right">
    Use the authorization code flow for browser-based and server-rendered applications.

    1. Redirect the user to the authorization endpoint.
    2. Receive the authorization code on your callback URL.
    3. Exchange the code for an access token.
    4. Use the token to call Vercel APIs on the user’s behalf.

    Keep the client secret on the server. Do not expose it in client-side code.
  </Tab>
  <Tab title="Access token" icon="lock">
    Use the access token in the same way as a personal access token, but treat the token as a user-granted credential with limited permissions.

    The token should map to the scopes approved during consent. If the user revokes access, stop using the token and force a fresh authorization flow.
  </Tab>
  <Tab title="Refresh token" icon="refresh-cw">
    If your OAuth app uses refresh tokens, store them securely and rotate them according to your app’s policy.

    Refresh tokens are sensitive credentials. Keep them out of logs, client bundles, and browser storage.
  </Tab>
</Tabs>

## Scope management

Scopes limit what a token or OAuth grant can access. You should request the minimum scopes required for the task and reject requests that need broader access than the user approved.

Use scopes to separate common integration tasks:

| Task | Suggested scope behavior |
| --- | --- |
| Read project metadata | Read-only scope |
| Create or update deployments | Write scope only when needed |
| Manage team settings | Team-admin scope with explicit approval |
| Access production resources | Production-specific scope or team restriction |

For API handlers, validate scope before you execute the operation. If the token does not include the required permission, return `403 Forbidden` and explain which capability is missing.

## Implementation

The examples below show a standard bearer token flow, a delegated OAuth flow, and a server-side verification check.

<CodeGroup tabs="TypeScript,Go,Ruby">
  ```typescript
  const token = process.env.VERCEL_TOKEN;

  if (!token) {
    throw new Error("Missing VERCEL_TOKEN");
  }

  const response = await fetch("https://api.example.com/v1/projects", {
    headers: {
      Authorization: `Bearer ${token}`,
    },
  });

  if (!response.ok) {
    throw new Error(`Request failed with status ${response.status}`);
  }

  const projects = await response.json();
  ```

  ```go
  package main

  import (
    "fmt"
    "net/http"
    "os"
  )

  func main() {
    token := os.Getenv("VERCEL_TOKEN")
    if token == "" {
      panic("Missing VERCEL_TOKEN")
    }

    req, _ := http.NewRequest("GET", "https://api.example.com/v1/projects", nil)
    req.Header.Set("Authorization", "Bearer "+token)

    client := &http.Client{}
    resp, err := client.Do(req)
    if err != nil {
      panic(err)
    }
    defer resp.Body.Close()

    fmt.Println(resp.StatusCode)
  }
  ```

  ```ruby
  require "net/http"
  require "uri"

  token = ENV["VERCEL_TOKEN"]
  raise "Missing VERCEL_TOKEN" if token.nil? || token.empty?

  uri = URI("https://api.example.com/v1/projects")
  request = Net::HTTP::Get.new(uri)
  request["Authorization"] = "Bearer #{token}"

  response = Net::HTTP.start(uri.hostname, uri.port, use_ssl: true) do |http|
    http.request(request)
  end

  puts response.code
  ```
</CodeGroup>

## Security tips

<Callout kind="alert">
  Treat access tokens and OAuth secrets as sensitive credentials. Store them in server-side secrets management, rotate them regularly, and never commit them to source control. If a token leaks, revoke it immediately and issue a replacement.
</Callout>

Use these baseline controls for every integration:

- Prefer short-lived credentials when your workflow supports them.
- Scope tokens to the smallest possible set of permissions.
- Separate personal, staging, and production access.
- Log authentication failures without printing secrets.
- Validate the team context before you perform write operations.

If you need a token for local development, use a dedicated development credential and keep it out of shared configuration files.
